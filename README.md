# 專題報告指導建議書

## 專題名稱

**結合生成式人工智慧與地理資訊之智慧旅遊行程規劃系統**

------------------------------------------------------------------------

## 一、基本資料

-   **研究領域：**
    人工智慧、地理資訊系統、智慧觀光、行程最佳化、網頁應用程式開發
-   **指導對象：** 資訊工程、資訊管理或相關領域之大學專題生及研究生
-   **指導目標：**
    建立具備研究依據、可實際操作、可驗證成效且具有展示價值的智慧旅遊行程規劃系統。

## 二、整體指導意見

本專題具有明確的實務應用價值，研究方向符合生成式人工智慧、地理資訊服務與智慧觀光的整合趨勢。傳統旅遊規劃通常仰賴使用者自行搜尋景點、評估交通時間、安排造訪順序及整理旅遊資訊，過程繁瑣且需要投入大量時間。

若能結合大型語言模型（LLM）的自然語言理解與內容生成能力，以及地理資訊系統（GIS）的空間分析與位置資訊處理能力，便有機會建立更符合使用者需求、路線安排更合理且資訊更容易理解的旅遊規劃服務。

**本專題最重要的研究價值，不應只是將生成式 AI 接入網站，而是證明 AI
生成的旅遊行程具有地理合理性、時間可行性及實際使用價值。**

因此，建議學生將研究重點放在以下四個面向：

-   **智慧化：** 能理解使用者的旅遊需求，並產生個人化行程。
-   **地理化：** 能運用景點座標、距離、交通時間及空間關係輔助規劃。
-   **可驗證：** 能以客觀指標檢驗行程的合理性與系統成效。
-   **可實作：** 能完成可操作的系統原型，而非僅停留於概念設計。

## 三、研究問題與研究目標之指導

### 3.1 建議明確界定研究問題

指導學生在撰寫緒論時，避免只描述「AI
很方便」或「旅遊規劃很花時間」，而應將實際問題轉化為可研究、可測試的研究問題。

  ---------------------------------------------------------------------------------------------------------------
  編號                    研究問題                                               預期驗證方向
  ----------------------- ------------------------------------------------------ --------------------------------
  RQ1                     生成式 AI 能否依據使用者偏好產生個人化旅遊行程？       需求符合率、使用者滿意度

  RQ2                     結合地理資訊後，能否提升景點順序與交通安排的合理性？   路線距離、交通時間、可行率

  RQ3                     加入規則驗證機制，能否降低 AI                          景點存在率、時間衝突率、錯誤率
                          生成錯誤資訊及不可行行程？                             

  RQ4                     相較於一般人工規劃或未使用地理資訊的 AI                規劃時間、品質評分、使用者評價
                          規劃方式，本系統是否具有實際效益？                     
  ---------------------------------------------------------------------------------------------------------------

以上研究問題可依學生實際能完成的功能，選擇三項作為核心研究問題，不宜為了增加研究規模而全部納入。

### 3.2 建議具體化研究目標

1.  建立旅遊景點資料庫，包含景點名稱、經緯度、類別、地址及必要的旅遊資訊。
2.  建立自然語言需求輸入機制，讓使用者描述旅遊日期、出發地、旅遊天數、興趣及交通方式。
3.  整合生成式 AI 與地理資訊服務，產生結構化且可呈現在地圖上的旅遊行程。
4.  設計行程檢核機制，確認景點位置、停留時間、交通時間及營業時間等限制。
5.  透過測試案例及使用者評估，驗證系統的可行性、正確性及實用價值。

**導師提醒：**
研究目標必須與後續實作成果及實驗指標一一對應。若目標寫了「最佳化路線」，實作及實驗就必須能證明路線品質有所改善。

## 四、系統架構與技術選用建議

建議採用分層式架構，將使用者介面、後端邏輯、AI
服務、地理資訊處理與資料儲存分開設計，以利除錯、測試及後續擴充。

### 4.1 建議系統架構

``` text
使用者介面
HTML、CSS、JavaScript 或其他前端框架
旅遊需求輸入、行程列表、地圖展示
                  |
                  v
後端應用服務
Python Flask／FastAPI
需求驗證、API 串接、行程資料整理、錯誤處理
          /                       \
         v                         v
生成式 AI 模組                 地理資訊模組
需求理解、行程生成             座標查詢、距離與路線分析
         \                         /
          v                       v
資料與驗證服務
景點資料庫、地圖服務 API、行程規則檢核
MySQL／SQLite、公開觀光資料或地圖供應商服務
```

實際部署時，AI 服務與地理資訊服務可由後端分別呼叫；景點資料庫、外部 API
及檢核模組應依需求獨立設計。

### 4.2 各項技術的指導建議

  ----------------------------------------------------------------------------------------
  技術或模組              建議用途                指導重點
  ----------------------- ----------------------- ----------------------------------------
  Python                  後端主要開發語言        程式模組化，避免所有功能集中於單一檔案

  Flask／FastAPI          建立後端 API            定義清楚的輸入、輸出及錯誤回應

  生成式 AI API           需求理解及行程生成      使用結構化輸出、限制條件及結果驗證

  Leaflet／Google Maps 等 地圖呈現與定位          依授權、費用、功能及部署條件選擇

  路線規劃 API            交通時間及路線取得      區分直線距離與實際道路距離

  MySQL／SQLite           儲存景點與行程資料      建立欄位規格、資料來源及更新方式
  ----------------------------------------------------------------------------------------

### 4.3 必須注意的技術風險

-   **AI 幻覺：**
    模型可能產生不存在的景點、錯誤地址或不正確的營業時間。應以可信資料來源驗證，而非直接相信模型輸出。
-   **地理資料品質：**
    景點座標、地址及營業資訊可能不完整或過期，必須記錄來源與更新日期。
-   **行程可行性：**
    景點順序看似合理，不代表實際交通時間足夠。應加入移動時間、停留時間、用餐時間及營業時間限制。
-   **API 限制：** 必須考量請求額度、網路失敗、金鑰管理及服務費用。
-   **隱私與資安：** API
    金鑰應存放在環境變數或安全設定中，不可直接寫入公開程式碼。

## 五、核心功能之指導建議

建議採取「先完成核心功能，再逐步擴充」的開發策略，避免學生在專題初期就同時開發帳號系統、社群功能、推薦模型及複雜的最佳化演算法，造成進度失控。

### 5.1 功能一：旅遊需求輸入

**必要功能**

收集旅遊地區、日期、天數、出發地、同行人數、交通方式、預算及興趣偏好。輸入資料應轉換為明確欄位，避免只傳送一段沒有結構的文字。

### 5.2 功能二：景點資料檢索

**必要功能**

從可信資料來源篩選符合旅遊地區、興趣與時間條件的景點，並取得可用的地理座標。應避免完全依賴
AI 臨時生成景點清單。

### 5.3 功能三：AI 行程生成

**必要功能**

依據使用者需求與候選景點產生每日行程，輸出景點名稱、造訪順序、建議抵達時間、停留時間及安排理由，並採用固定資料格式供後端處理。

### 5.4 功能四：地理資訊整合

**必要功能**

將景點標示於互動式地圖，計算或取得景點間的實際交通路線及預估時間，並檢查每日行程是否符合時間限制。

### 5.5 功能五：行程驗證與調整

**核心差異化**

當交通時間過長、景點已休息或行程超出可用時間時，系統應提出警告、重新排序或替換景點，而不是只顯示
AI 產生的結果。

### 5.6 建議的最小可行產品（MVP）

第一階段建議只完成以下閉環：

1.  使用者輸入旅遊需求。
2.  系統取得可驗證的候選景點資料。
3.  AI 產生結構化行程。
4.  後端驗證景點及時間安排。
5.  地圖顯示景點與路線。
6.  使用者能查看結果並修改部分條件。

完成以上流程後，再評估是否增加登入、收藏、旅遊預算計算、多日路線最佳化及個人化推薦等功能。

## 六、研究方法與實驗設計建議

這是本專題能否從「軟體開發作品」提升為「具有研究價值的學術專題」的關鍵。

建議學生採用系統開發與實證評估相結合的方法，並明確記錄測試條件、資料來源、實驗流程及評估標準。

### 6.1 建議研究流程

1.  **問題定義與文獻探討：** 整理智慧觀光、生成式 AI、GIS
    與路線規劃相關研究。
2.  **需求分析與系統設計：**
    定義使用者需求、功能需求、資料結構及系統架構。
3.  **系統實作：** 完成後端 API、AI 行程生成、地理資訊與地圖展示。
4.  **功能與整合測試：** 測試輸入錯誤、資料缺漏、交通限制及 API
    失敗情境。
5.  **實驗與成效評估：** 比較不同規劃方式，蒐集客觀指標與使用者評價。
6.  **結果分析與報告撰寫：** 分析研究結果、限制與貢獻，提出改善方向。

### 6.2 建議建立三組比較實驗

  實驗組別   規劃方式                            主要研究目的
  ---------- ----------------------------------- ------------------------
  A 組       一般生成式 AI 直接生成行程          建立基準組
  B 組       生成式 AI 搭配景點資料與地理資訊    檢驗地理資訊的影響
  C 組       生成式 AI、地理資訊及行程規則驗證   檢驗完整系統的改善效果

三組應盡量使用相同的使用者需求、景點資料範圍及測試情境。若要比較生成時間，也應記錄模型、提示詞、API
設定及執行環境，避免將其他因素造成的差異誤認為系統效果。

### 6.3 建議採用的評估指標

#### （一）地理與路線合理性

-   **景點有效率：** 行程中可由可信資料確認的景點比例。
-   **路線總距離：** 各景點之間實際道路距離的總和。
-   **交通時間：** 使用相同路線服務與交通模式取得的估計時間。
-   **路線可行率：** 符合既定時間、營業時間及交通限制的行程比例。

#### （二）效率與資源使用

-   **行程生成時間：** 從送出需求至取得可用行程的時間。
-   **人工修正量：** 使用者為了使行程可行而必須修改的項目數。
-   **API 呼叫次數與費用：** 評估系統的實際營運成本。

#### （三）使用者體驗與需求符合度

-   **偏好符合度：** 景點類型、預算及交通方式是否符合需求。
-   **易用性：** 使用者是否能順利完成行程規劃任務。
-   **滿意度：** 使用者對行程合理性、資訊完整性與個人化程度的評價。

景點有效率可定義為：

\[ `\text{景點有效率}`{=tex}=
`\frac{\text{經資料來源確認有效的景點數}}`{=tex}
{`\text{行程中的景點總數}`{=tex}}`\times100`{=tex}% \]

景點有效不等於整段行程可行；即使每個景點都存在，也可能因交通時間、營業時間或停留時間而無法完成。

**導師建議：**
不應預先宣稱完整系統一定優於基準組。應先定義指標，再依實驗結果分析改善幅度、例外情況及可能原因。

1.  優先閱讀與研究問題直接相關的期刊論文、研討會論文及具公信力的官方文件。

## 十二、預期研究貢獻與未來發展方向

### 12.1 預期貢獻

-   **技術整合貢獻：** 將生成式 AI
    的自然語言處理能力與地理資訊服務整合，建立由需求輸入到行程呈現的規劃流程。
-   **系統實務貢獻：**
    以景點資料、交通資訊及行程規則檢核降低單純文字生成可能產生的錯誤。
-   **評估方法貢獻：**
    透過基準組比較與量化指標，分析地理資訊及驗證機制對行程品質的影響。

### 12.2 後續可擴充方向

1.  **個人化推薦機制：**
    根據使用者興趣、過往選擇及同行對象調整景點排序，並評估推薦結果是否更符合需求。
2.  **多景點路線最佳化：**
    在景點價值、總交通時間、開放時段及每日行程長度之間建立明確的最佳化目標與限制條件。
3.  **即時資訊整合：**
    在資料來源允許的情況下，整合天氣、交通、營業時間及臨時公告，提供動態行程調整建議。

以上均屬未來發展方向，不建議全部列為目前專題的必要實作範圍。學生應優先完成可展示、可測試及可驗證的核心系統。

## 十四、導師總結：三項最重要的原則

1.  **先求正確，再求智慧：** 景點資料與交通資訊必須可靠，不能只追求 AI
    生成速度。

3.  **先有證據，再下結論：**
    所有關於系統優勢、效率提升及使用者滿意度的主張，都應有測試或實驗結果支持。

這三項原則將直接影響本專題最終的學術品質與實作成果。
